# Лучшие практики CI/CD для AI-управляемой разработки

Этот документ описывает лучшие практики CI/CD, которые значительно повышают качество и надёжность AI-управляемых рабочих процессов разработки. При правильной настройке AI-решатели вынуждены итерировать с CI/CD проверками до прохождения всех тестов, обеспечивая соответствие кода высочайшим стандартам.

## Почему CI/CD важен для AI-разработки

AI-решатель инструктирован обращать внимание на CI/CD проверки в каждом pull request. Это создаёт мощный цикл обратной связи:

1. **AI создаёт решение** — Решатель генерирует код на основе требований задачи
2. **CI/CD валидирует решение** — Автоматические проверки верифицируют качество кода
3. **AI итерирует до прохождения** — Решатель исправляет проблемы до прохождения всех проверок
4. **Качество гарантировано** — Код не сливается без прохождения всех gate-ов

Этот подход обеспечивает консистентное качество независимо от того, состоит ли команда из людей, AI или и тех, и других.

## Ключевые принципы CI/CD

### 1. Запускайте проверки только при релевантных изменениях файлов

**Запускайте проверки только когда изменились релевантные файлы.** Это драматически снижает затраты на CI и время выполнения.

Используйте job `detect-changes` в начале workflow для определения, какие категории файлов изменились:

```yaml
jobs:
  detect-changes:
    runs-on: ubuntu-latest
    outputs:
      code-changed: ${{ steps.changes.outputs.code }}
      docs-changed: ${{ steps.changes.outputs.docs }}
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 2
      - name: Detect changes
        id: changes
        run: |
          if git diff --name-only HEAD~1 | grep -qE '\.(py|mtc|anum)$'; then
            echo "code=true" >> $GITHUB_OUTPUT
          else
            echo "code=false" >> $GITHUB_OUTPUT
          fi
          if git diff --name-only HEAD~1 | grep -qE '\.md$'; then
            echo "docs=true" >> $GITHUB_OUTPUT
          else
            echo "docs=false" >> $GITHUB_OUTPUT
          fi
```

Затем gate-ите каждый job на релевантном выводе:

```yaml
test-suites:
  needs: [detect-changes]
  if: needs.detect-changes.outputs.code-changed == 'true'
  # ...
```

**Что исключать из определения "изменений кода":**

- Markdown файлы (`*.md`) — изменения только в документации не требуют changeset-файлов
- Папка `.changeset/` — метаданные changeset не являются кодом
- Папки `data/` и `experiments/` — непроизводственный контент
- Файлы `.gitkeep` — файлы-заглушки без функционального влияния

**Что всегда запускает проверки при изменении:**

- Файлы исходного кода (`.py`, `.mtc`, `.anum` и т.д.)
- Workflow-файлы CI/CD (`.github/workflows/*.yml`)
- Файлы зависимостей (`requirements.txt`, `pyproject.toml`)

### 2. Ограничения размера файлов

**Устанавливайте максимум 1000-1500 строк на файл кода.**

Это ограничение полезно как для AI, так и для разработчиков-людей:

- AI-модели могут читать и понимать целые файлы в рамках контекстных окон
- Люди могут навигировать и понимать файлы без когнитивной перегрузки
- Это форсирует модульную, хорошо организованную архитектуру кода

Пример проверки в CI (bash):

```bash
find . -name "*.py" -type f | while read -r file; do
  line_count=$(wc -l < "$file")
  if [ "$line_count" -gt 1500 ]; then
    echo "ERROR: $file имеет $line_count строк (лимит: 1500)"
    exit 1
  fi
done
```

### 3. Автоматическое форматирование кода

Консистентное форматирование устраняет дискуссии о стиле и снижает шум в diff-ах:

| Язык   | Инструмент        |
|--------|-------------------|
| Python | Ruff, Black       |
| JSON   | jq, prettier      |

### 4. Статический анализ и линтинг

Ловите баги и проверяйте паттерны до код-ревью:

| Язык   | Инструменты          |
|--------|----------------------|
| Python | Ruff + mypy          |

### 5. Порядок job-ов "быстро отказывай"

**Запускайте быстрые проверки до медленных** для максимально быстрой обратной связи:

```
Быстрые проверки (~7-30с):      Медленные проверки (~1-10 мин):
├── lint (формат + Ruff)         ├── test-suites (unit-тесты)
└── check-file-line-limits       └── integration-tests
```

Gate-ите медленные проверки на быстрых:

```yaml
test-suites:
  needs: [lint, check-file-line-limits]
  if: |
    always() &&
    !cancelled() &&
    !contains(needs.*.result, 'failure')
```

### 6. Валидация реального результата слияния

**CI должен тестировать то, что реально будет слито, а не устаревший snapshot PR.**

Когда PR открыт против базовой ветки, которая потом получила новые коммиты, GitHub merge preview может устареть. Симулируйте свежее слияние перед запуском проверок:

```yaml
- name: Симуляция свежего слияния с базовой веткой (только PR)
  if: github.event_name == 'pull_request'
  env:
    BASE_REF: ${{ github.base_ref }}
  run: |
    git config user.email "github-actions[bot]@users.noreply.github.com"
    git config user.name "github-actions[bot]"
    git fetch origin "$BASE_REF"
    BEHIND_COUNT=$(git rev-list --count HEAD..origin/$BASE_REF)
    if [ "$BEHIND_COUNT" -gt 0 ]; then
      git merge origin/$BASE_REF --no-edit || \
        (echo "::error::Конфликт слияния! PR должен быть rebase-ен перед слиянием." && exit 1)
    fi
```

Это гарантирует, что lint, проверка размера файлов и другие проверки валидируют финальное слитое состояние.

### 7. Pre-commit хуки

Локальные gate-ы качества предотвращают попадание сломанных коммитов в CI:

1. Проверка и автоисправление форматирования
2. Lint и статический анализ
3. Проверка типов (где применимо)
4. Валидация размера файлов

Этот подход "сдвига влево" ловит проблемы немедленно, а не ждёт CI.

### 8. Контроль конкурентности

**Предотвращайте конфликты нескольких запусков workflow:**

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  # Отменяйте старые запуски на main, чтобы всегда релизить последнюю версию
  cancel-in-progress: ${{ github.ref == 'refs/heads/main' }}
```

Используйте `!cancelled()` вместо `always()` в условиях job-ов, чтобы отмена правильно распространялась через граф job-ов.

### 9. Валидация документации

**Валидируйте файлы документации в CI так же, как код:**

- Проверяйте ограничения размера файлов (напр., максимум 2500 строк для docs)
- Проверяйте наличие обязательных секций в ключевых документах
- Проверяйте битые ссылки с помощью инструментов типа `lychee`

```yaml
validate-docs:
  needs: [detect-changes]
  if: needs.detect-changes.outputs.docs-changed == 'true'
  steps:
    - name: Проверка документации
      run: |
        # Проверка размеров файлов документации
        find docs/ -name "*.md" -type f | while read -r file; do
          line_count=$(wc -l < "$file")
          if [ "$line_count" -gt 2500 ]; then
            echo "WARNING: $file имеет $line_count строк"
          fi
        done
```

## Стратегия обеспечения качества

Реализуйте подход "защиты в глубину":

```
Машина разработчика    →    CI/CD Pipeline      →    Релиз
├── Pre-commit хуки        ├── detect-changes       ├── Все проверки проходят
├── Локальные тесты        ├── lint                 └── Слияние в main
└── IDE интеграция         ├── check-file-limits
                           ├── test-suites
                           └── validate-docs
```

Каждый слой ловит разные проблемы, гарантируя, что проблемный код не попадёт в продакшн.

## Начало работы

1. **Настройте GitHub Actions workflow** в `.github/workflows/ci.yml`
2. **Настройте pre-commit хуки** для локальных проверок
3. **Добавьте проверки линтинга** (Ruff для Python)
4. **Начните разработку** со всеми настроенными лучшими практиками

AI-решатели автоматически будут учитывать и итерировать со всеми настроенными проверками, производя вывод более высокого качества, чем репозитории без CI/CD enforcement-а.
