## Почему важны лучшие практики

Качество AI-управляемой разработки существенно зависит от:

1. **Чёткие требования к задачам** — Размытые задачи порождают размытые решения
2. **Надёжные CI/CD пайплайны** — AI-решатели итерируют до прохождения всех проверок, гарантируя качество
3. **Качественный промптинг** — Универсальные промпты помогают AI проводить глубокий анализ и избегать типичных ошибок
4. **Архитектурная дисциплина** — Консистентная структура кода проще для навигации и расширения AI

Каждый из этих слоёв усиливает другие: хорошие требования + надёжный CI/CD + качественные промпты = стабильно отличные автоматизированные решения.

## Универсальные промпты

Следующие промпты можно добавлять как комментарии к любой GitHub issue или pull request для направления поведения AI-решателя.

### Промпт глубокого анализа бага

Используйте, когда баг требует тщательного исследования перед попыткой исправления:

```
Пожалуйста, проведи глубокий анализ этой проблемы:
1. Загрузи все релевантные логи, вывод ошибок и данные воспроизведения в ./docs/case-studies/issue-{id}/
2. Поищи в интернете похожие проблемы, известные причины и решения сообщества
3. Восстанови полную хронологию: когда это началось, что изменилось, какова последовательность событий, вызывающих баг?
4. Определи истинную корневую причину (не только симптом)
5. Предложи несколько подходов к решению с компромиссами
6. Реализуй лучшее решение с тестами
7. Проверь, что CI/CD проверки проходят перед финализацией
```

### Промпт глубокого анализа фичи

Используйте, когда запрос фичи требует исследования и проектирования перед реализацией:

```
Пожалуйста, проведи глубокий анализ этого запроса функциональности:
1. Собери весь релевантный контекст и примеры в ./docs/case-studies/issue-{id}/
2. Поищи в интернете, как похожие фичи реализованы в аналогичных инструментах
3. Проанализируй компромиссы: производительность, поддерживаемость, обратная совместимость
4. Предложи детальный план реализации с альтернативными подходами
5. Реализуй выбранный подход с тестами
6. Обнови документацию, чтобы отразить новую функциональность
7. Проверь, что все CI/CD проверки проходят перед финализацией
```

### Универсальный промпт валидации

Добавьте как комментарий перед финализацией любого решения, чтобы ничего не было упущено:

```
Перед пометкой как завершённое, пожалуйста проверь:
1. Все требования из исходной задачи выполнены
2. Все обсуждения из комментариев PR/issue решены
3. Все CI/CD проверки проходят (нет ошибок линтера, все тесты зелёные)
4. Никакие ранее работающие функции не сломаны
5. Код следует существующему стилю и соглашениям репозитория
6. Документация обновлена, если поведение изменилось
7. Нет отладочного кода, временных хаков или TODO
8. Changeset (если требуется) присутствует и корректен
```

### Промпт режима планирования

Используйте, когда хотите, чтобы AI предложил план перед написанием кода:

```
Пожалуйста, войди в режим планирования для этой задачи:
1. Собери все релевантные данные в ./docs/case-studies/issue-{id}/
2. Прочитай все связанные исходные файлы, тесты и документацию
3. Поищи в интернете, если нужны внешние знания
4. Предложи детальный пошаговый план реализации
5. Перечисли все файлы, которые будут созданы или изменены
6. Определи риски и граничные случаи
7. Дождись одобрения перед написанием любого кода
```

### Промпт максимальной тщательности

Используйте для сложных задач, где нужны полные возможности AI:

```
Реши эту задачу с максимальной тщательностью:
- Используй --model opus --think max для глубокого рассуждения
- Загрузи и проанализируй все релевантные логи
- Проведи онлайн-исследование похожих проблем и решений
- Напиши комплексные тесты, покрывающие граничные случаи
- Добавь детальную трассировку/логирование, которое остаётся в коде, но выключено по умолчанию
- Убедись, что все CI/CD проверки проходят
- Не оставляй камня на камне
```

## Написание качественных задач

Качественные требования к задачам — фундамент качественных AI-решений. Изучайте закрытые задачи и слитые PR в этом репозитории для примеров.

### Чеклист написания задачи

- [ ] **Чёткое описание проблемы** — Что сломано или отсутствует? Каково ожидаемое vs фактическое поведение?
- [ ] **Шаги воспроизведения** — Как можно надёжно воспроизвести проблему?
- [ ] **Контекст** — Какие файлы, функции или компоненты затронуты? Дайте ссылки на них.
- [ ] **Критерии приёмки** — Какие конкретные условия определяют "готово"? Перечислите их явно.
- [ ] **Примеры** — Включите фрагменты кода, сообщения об ошибках или скриншоты как доказательства.
- [ ] **Ограничения** — Есть ли то, что решение НЕ должно делать (напр., не должно ломать X, не должно добавлять зависимость)?
- [ ] **Приоритет** — Насколько это срочно? Каково влияние, если не исправить?

### Шаблоны требований к задачам

**Для багов:**

```
## Проблема
[Одно предложение, описывающее неправильное поведение]

## Шаги воспроизведения
1. [Точная команда или действие]
2. [Что происходит]
3. [Что должно происходить вместо этого]

## Гипотеза корневой причины
[Опционально: ваше лучшее предположение, почему это происходит]

## Критерии приёмки
- [ ] [Конкретное измеримое условие 1]
- [ ] [Конкретное измеримое условие 2]
- [ ] Все CI/CD проверки проходят
```

**Для фич:**

```
## Цель
[Одно предложение, описывающее новую возможность]

## Мотивация
[Зачем это нужно? Какую проблему это решает?]

## Предлагаемая реализация
[Опционально: ваше предложение по реализации]

## Критерии приёмки
- [ ] [Функция работает в сценарии A]
- [ ] [Функция работает в сценарии B]
- [ ] Тесты покрывают новое поведение
- [ ] Документация обновлена
- [ ] Все CI/CD проверки проходят
```

## Улучшение архитектуры

Для улучшения архитектуры кодовой базы с помощью AI используйте этот промпт, ссылающийся на Принципы архитектуры кода:

```
Пожалуйста, проанализируй эту кодовую базу на соответствие принципам архитектуры из:
https://raw.githubusercontent.com/link-foundation/code-architecture-principles/refs/heads/main/README.md

Для каждого принципа, который нарушен или может быть лучше применён:
1. Определи конкретное место (файл:строка), где происходит нарушение
2. Объясни, почему это нарушение и каково его влияние
3. Предложи конкретный рефакторинг с примером кода до/после
4. Расставь приоритеты по влиянию: высокий/средний/низкий

Особое внимание удели:
- Ограничениям размера файла (максимум 1000-1500 строк)
- Принципу единственной ответственности
- Разделению ответственностей
- Тестируемости
- Явным интерфейсам и минимальной связанности
```

### Краткое содержание ключевых принципов архитектуры

Для глубокого руководства по написанию поддерживаемого кода см. [Принципы архитектуры кода](https://github.com/link-foundation/code-architecture-principles), которые охватывают:

**Универсальные принципы:**

- **Модульность**: Разбивайте системы на маленькие, тестируемые части
- **Разделение ответственностей**: Высокая связность, низкая связанность
- **Абстракция**: Скрывайте детали реализации за стабильными интерфейсами
- **Иммутабельность**: Предпочитайте создание новых значений мутации
- **Быстрый отказ**: Валидируйте ввод на границах системы

**Ключевые рекомендации:**

1. Проектируйте API, которые очевидно правильно использовать и трудно использовать неправильно
2. Экспонируйте функциональность для расширяемости, а не прячьте внутренности
3. Делайте невалидные состояния невозможными через продуманное моделирование данных
4. Перемещайте побочные эффекты на границы системы; держите ядро логики чистым
5. Используйте системы типов для моделирования валидных форм данных
6. Пишите маленькие, сфокусированные функции, которые делают одну вещь хорошо
7. Предпочитайте композицию наследованию и сложности

## Лучшие практики CI/CD

CI/CD пайплайны — основа качества AI-управляемой разработки. Когда проверки настроены:

- AI-решатели **вынуждены итерировать** до прохождения всех тестов
- Качество кода **гарантировано** независимо от человеческого или AI авторства
- Проблемы обнаруживаются **рано**, до попадания в продакшн

См. **[CI-CD-BEST-PRACTICES.md](./CI-CD-BEST-PRACTICES.md)** для полного руководства.

## Использование субагентов

AI может координировать несколько агентов, работающих параллельно. Используйте субагентов для:

### Когда использовать субагентов

- **Независимое параллельное исследование** — Один агент ищет в логах, пока другой читает исходный код
- **Защита основного контекста** — Выгружайте чтение больших файлов или длинные поиски на субагентов
- **Специализированные задачи** — Используйте выделенного агента для документации, другого для тестов
- **Перекрёстная проверка** — Пусть несколько агентов предложат решения независимо, затем сравните

### Паттерны субагентов

**Параллельное исследование:**

```
Запусти субагентов параллельно для:
- Агент 1: Прочитай все исходные файлы, связанные с [областью функциональности]
- Агент 2: Поищи недавние задачи и PR, связанные с этой проблемой
- Агент 3: Прочитай все тестовые файлы, чтобы понять ожидаемое поведение
Затем синтезируй находки перед реализацией.
```

**Поэтапная работа:**

```
Этап 1 (исследовательский субагент): Собери и проанализируй все релевантные данные
Этап 2 (планирующий субагент): Спроектируй подход к реализации
Этап 3 (реализация): Напиши и протестируй решение
Этап 4 (валидирующий субагент): Запусти все проверки и проверь требования
```

**Итерация по чеклисту:**

```
Поддерживай чеклист всех требований из задачи.
После каждого шага отмечай завершённые пункты.
Итерируй, пока чеклист полностью не завершён и все CI/CD проверки не проходят.
Никогда не отмечай задачу выполненной, пока не проверено, что она работает.
```
